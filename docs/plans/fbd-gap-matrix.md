# FBD ⇄ BetterDisplay gap matrix

Inputs: `betterdisplay-feature-inventory.md` (the reference) and `fbd-feature-inventory.md` (FBD).
Every BetterDisplay behaviour below is **paraphrased** from observed behaviour — see the reference
document's wording policy. Route column names the concrete macOS path and classifies it as
**public** · **private-already-ledgered** (already in `docs/PRIVATE_APIS.md`) · **new-private**
(would need a new ledger entry).

Effort: **XS** ≤ ½ day · **S** ~1 day · **M** ~2–3 days · **L** ~1 week · **XL** > 1 week.
Sorted by value ÷ effort within each tier.

## Deliberately **not** pursued (and why)

| item | why not |
|---|---|
| **Pro licence machinery** — purchase, activation, deactivation, trial, per-install activation counts, licence-server reachability | Out of scope by the mission itself: FBD is free with no licence server. Nothing in this category is ported or imitated. |
| **Direct XDR upscaling (built-in panel, Apple's own path)** | `IOMobileFramebufferOpen` is entitlement-gated (`kIOReturnNotPrivileged`) and BetterDisplay's own direct path needs a privileged helper. FBD's software path already works on macOS 27 and is live-verified — spending effort here trades a working path for a blocked one. |
| **HDMI-CEC, DisplayLink, Wake-on-LAN, Sidecar connection control** | Each needs hardware that is not attached here (CEC-capable TV, DisplayLink adapter, a second Mac), so they could be *implemented but never verified*. Adding unverifiable feature surface contradicts the repo's own "verify before claiming" rule. |
| **Privileged helper** | FBD deliberately has none; introducing one changes the app's security and installation story far beyond a parity feature. |
| **TV service/hospitality menus, pairing flows beyond what FBD already has** | Low value, vendor-specific, and partly tied to the smart-TV ecosystems FBD already reaches via `fbdcli tv`. |
| **Everything in "Tier 3" #22/#23/#27** | Blocked on private APIs FBD has not identified, with a failure mode (an unusable display) that cannot be tested safely on the only attached display. Recorded as known, not attempted. |
| **~40 artistic compositor filters as a *first* priority** | High implementation volume, low core value; the filter *framework* already exists, so filters can be added incrementally later (Tier 2 #19). |

## Recommended top-N (what I propose to build in Phase 4)

Chosen for **value ÷ effort**, for being **verifiable on this machine**, and for landing entirely
behind seams that already have tests.

**N = 8.**

| rank | gap (#) | why it made the cut |
|---|---|---|
| 1 | Per-property configuration protection (#1) | The single biggest *real* capability gap — FBD protects one opaque blob, BetterDisplay protects nine properties independently. Everything it needs is public or already ledgered, and `ConfigProtectionController` is already an injectable, tested seam. |
| 2 | Group synchronisation + activation policy (#2, #3) | BetterDisplay's headline organisational feature, and FBD already has the group store and `syncBrightness`. The new part is a **pure policy layer**, so it is cheap to test exhaustively. |
| 3 | Startup safe mode (#7) | A safety feature, not a convenience: it is the documented escape hatch for a bad EDID override, and FBD ships EDID overrides. Tiny, fail-closed, and fully unit-testable. |
| 4 | Resolution favourites + mode-list breadth + refresh/VRR list (#4, #5, #6) | One coherent "display mode" workstream using only already-ledgered symbols. Makes FBD's existing mode support match BetterDisplay's discoverability. |
| 5 | Device-control policies + editable nits ranges + combined-curve points (#9, #10) | Closes the brightness-model gap without a new API: both `CombinedBrightness` and `XDRBoostPlanner` are pure and already property-swept, so new parameters are cheap to prove correct. |
| 6 | Dim on screen saver / lock (#8) | Small, self-contained, and pairs with the existing dim-to-black overlay. |
| 7 | Connection-management extras (#11) + auto-brightness CLI surface (#12) | Cheap parity wins at chokepoints that already exist and are already guarded. |
| 8 | Keyboard-control target (#15) | Turns FBD's fixed media-key routing into BetterDisplay's target-selection model, entirely as a pure routing matrix over the existing tested `MediaKeyRouter`. |
